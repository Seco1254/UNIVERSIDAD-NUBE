CARA 1 · Pruebas y patrones

DPOO · Examen 2

★FORMA · ¿veo el código?

C. BLANCA: SÍ veo código · estructura interna · verificación · la hace el dev. Técn.: cobertura, pruebas de API, inyección de fallos, mutación, estáticas.

C. NEGRA: NO veo código · funcionalidad (el qué, no el cómo) · validación · tester/QA. Técn.: particiones, bordes, tabla de decisión, pares, casos de uso/HU.

Mi equipo → blanca · Tercero (pasarela) → negra · la unión app + pasarela → integración. Son complementarias.

★NIVELES · ¿qué tan grande?

1Unitaria: 1 unidad (método/clase/interfaz) AISLADA. Stub = datos fijos · Mock = además verifica llamadas. Temprano, TDD. 2Integración: módulos JUNTOS → interfaces e interacciones. Bottom-up ↑ · top-down ↓ · big-bang (todo de una). 3Sistema: TODO vs requerimientos (lo hace el equipo). Destructiva (carga extrema) · no destructiva (rutina) · inyección de fallos (chaos monkey). 4Aceptación: el CLIENTE decide. De usuario · operacional (listo p/ producción) · contractual · alfa/beta.

✗ Regresión NO es un nivel.

★TÉCNICAS · ¿cómo escojo los casos?

Especificación (negra):

  • Particiones de equivalencia: grupos tratados igual → 1 representante c/u (también los inválidos). Envío: 0–39999 / 40000+ → 20000 y 60000.
  • Valores de borde (BVA): frontera ± 1 → 39999 · 40000 · 40001. Caza el < vs <=.
  • Tabla de decisión: combinaciones de condiciones (2 cond. → 4 casos; 3 → 8).
  • Transición de estados: secuencias (PIN: 3 errores → bloqueada). Pocos valores.

Estructura (blanca) = COBERTURA: instrucciones (c/ línea) < ramas (c/ lado del if) < condiciones (c/ cond. T y F) < cond. múltiples (todas las combinaciones). Eclipse: verde / rojo / amarillo. «No todo el código; sí todos los requerimientos».

Experiencia: exploración (sin guion) · adivinar errores (vacío, null, 0, negativos).

★4 FASES + GIVEN-WHEN-THEN

1Definir la estructura · @BeforeEach setUp() · GIVEN (dado) 2Ejecutar · llamar el método · WHEN (cuando) 3Chequear · assert · THEN (entonces) 4Destruir la estructura · @AfterEach tearDown() · vuelve al estado inicial

Por qué: estado inicial · no cambiar el estado del sistema · pruebas NO acopladas (independientes).

★MÁS PRUEBAS

  • Regresión = volver a correr tras un cambio: reset all (todas, la más costosa) · test selection · prioritization (impacto, criticidad, frecuencia).
  • TDD: pruebas → fallan → implementar → pasan → refactorizar.
  • Falla = assert no se cumple («expected… but was») · Error = excepción · Éxito. assume → ABORTA.
  • assertEquals(ESPERADO, obtenido, margen) · assertThrows(X.class, () -> …) · lo que verifica = lo que está en el assert.
  • Principios: pequeñas (1 resp.) · independientes · no quemar valores · asserts de alto nivel.

★PATRONES · ¿está bien?

SINGLETON (creacional): ① private static instancia ② constructor private ③ public static getInstancia() ④ if (instancia == null) crea.
✗ constructor public → más de uno · ✗ getInstancia sin static → NO compila · ✗ sin if → uno nuevo cada vez.

PROXY (estructural, el del profe): MISMA interfaz que el real · el cliente conoce SOLO la interfaz · solo el proxy le habla al real · controla el acceso (remoto, costoso). En Java: RMI.

ADAPTER (estructural): implementa MI interfaz · tiene un atributo de la clase ajena · traduce. CAMBIA la interfaz.

FACADE (estructural): 1 método simple → muchos pasos en muchas clases. El cliente no ve los subsistemas.

STRATEGY (comportamiento): interfaz + 1 clase x variante · el contexto delega SIN if / instanceof (si no, viola la O).

○FAMILIAS GoF (si cabe)

Creacionales: Abstract Factory, Builder, Factory Method, Prototype, Singleton.

Estructurales: Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy.

Comportamiento: Chain of Resp., Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor.

Elementos de un patrón: Intent · AKA · Motivation · Applicability | Structure · Participants · Collaborations | Consequences | Implementation · Sample code · Known uses | Related. (Alexander 1977 → GoF 1995)

CARA 2 · Contexto, historias, diseño y errores

DPOO · Examen 2

★CONTEXTO DE UNA EMPRESA

  • Funcional = lo que HACE.
  • No funcional = qué tan BIEN: rendimiento, carga, disponibilidad, seguridad, usabilidad, plataforma. Debe ser medible.
  • Regla del dominio = regla del NEGOCIO (máx. 1 préstamo; total = platos + envío + propina).
  • Restricción = límite del PROYECTO: presupuesto, legado (BD que ya existe), equipo, plazo, tecnología impuesta.

✗ «rápido» = NF mal escrito (sin medida) · «en Java» = restricción.

★HISTORIAS DE USUARIO

Como [rol] quiero [acción] para [beneficio] + criterios VERIFICABLES, en given-when-then → cada criterio = 1 prueba.

✗ tarea técnica («crear tabla») · ✗ sin beneficio · ✗ vaga («que funcione bien»).

★DISEÑO

  • La responsabilidad va a quien TIENE la información. Cadena de getters = mal ubicada.
  • Estereotipos: contenedor (sabe datos) · estructurador (colecciones, busca) · proveedor de servicios (trabaja p/ otros, pasivo) · coordinador (reparte, decide poco) · controlador (decide y dirige) · interfaz (habla con el exterior).
  • Ñam: Pedido = controlador · Despachador = coordinador · Catálogo / Manejador de carritos = estructurador · Conector DB = proveedor · Pasarela / Mapas = interfaz.
  • Control: centralizado (pocos controladores + clases get/set; «AlgoService» gigante; fácil hallar los puntos críticos) · delegado (coordinadores; menos acoplamiento) · disperso (sin centro; un cambio afecta a muchos).
  • Colaboraciones ✗: muchas conexiones desde fuera del vecindario · muchos mensajes de bajo nivel (→ 1 mensaje grueso) · muchos caminos condicionales.

★4 RECOMENDACIONES + SOLID

↓ complejidad · pensar en los cambios · ↓ acoplamiento · inyección de dependencias (por constructor o setter: RECIBIR, no crear ni buscar).

S 1 razón p/ cambiar · O agregar sin modificar (if x tipo = ✗) · L la hija cumple lo del padre (lanza o deja vacío = ✗) · I interfaces pequeñas · D depender de interfaces (new concreto adentro = ✗).

(si cabe) Responsabilidades: las gruesas primero · sin «manejar/gestionar» · no repetir.

★ERRORES · leer código

  • finally SIEMPRE corre · catch específico ANTES del general (si no, no compila).
  • Checked (extends Exception) → catch o throws, si no NO COMPILA · unchecked (RuntimeException) no obliga.
  • Diseño del error: identificar → planear (probabilidad, prevenir, impacto, corregir) → diseñar (detectar activa/pasiva; reaccionar CERCA; nadie atrapa lo que no puede manejar; convertir bajo → alto nivel) → documentar.
  • 9 estrategias: prevenir · inacción · balk (avisar al que pidió) · suspensión temporal · acciones provisionales · alternativa · apelar a una autoridad superior · rollback · reintentar (no de inmediato).
  • Regiones de confianza: mi equipo > otros equipos > otras empresas · catch vacío = ✗.
